# Стиль коду C#

Застосовується до всіх `.cs` файлів проєкту.

## Структура файлу і класу

- **Namespace повторює шлях від папки** під `Assets/` (наприклад, `_Project.Develop.Runtime.Infrastructure.DI`). Префікс `_Project.` — обов'язковий.
- **Один тип — один файл**, ім'я файлу = ім'я типу.
- **Порядок членів класу**: Поля → Конструктор → Властивості → Методи.
- **Усередині кожного блоку** — порядок за модифікатором доступу: `public` → `protected` → `private`.
- **Події** належать до полів (вище за всі інші поля).
- **Модифікатори доступу пишемо завжди явно** — крім членів інтерфейсу (там мається на увазі `public`).

## Іменування

- `camelCase` — локальні змінні, параметри (`canConnect`, `waterAmount`).
- `_camelCase` — `private` поля (`_pressure`, `_animator`).
- `PascalCase` — `public` і `protected` поля (protected іменуємо як public, без підкреслення), **властивості** (завжди), методи, класи, інтерфейси, структури, enum, namespace.
- `UPPER_SNAKE_CASE` — `const` (з будь-яким модифікатором доступу): `private const float MAX_PRESSURE = 10f;`.
- `static readonly` і `readonly` поля — **не константи**, іменуємо за правилом полів (`PascalCase` для public, `_camelCase` для private).
- Інтерфейси з префіксом `I`: `ISceneLoader` + реалізація `SceneLoader`.
- **Bool-методи**: `IsX` / `CanX` / `HasX` (`IsEmpty()`, `CanConnect()`). Уникаємо `CheckX` — розмита назва, у такі методи часто пролазять побічні ефекти.
- **`bool TryX(...)`** — методи, які можуть не виконатися і повертають прапорець успіху (`TryConnect`).
- **Властивості-прапорці** — за тією ж схемою: `IsEmpty`, `IsConnected`.
- **Події** іменуємо в минулому часі (`Connected`, `Extinguished`); обробники — `OnX` (`OnConnected`); інколи допустимо без `On`.
- **Іменники** — для класів, полів, властивостей; **дієслова** — для методів.
- **Точні назви, без скорочень**. Назва має відображати суть; економія на довжині нічого не дає.
- **Множина для колекцій** (`hoses` — список шлангів, `hose` — один шланг).
- **Без тавтології**: `Hose.Connect()`, а не `Hose.HoseConnect()` (на місці виклику вже видно `hose.`).
- **Без розмитих назв** (`GameManagerController`, `…Manager`, `…Helper`) — зазвичай клас можна назвати точніше, щоб назва відображала відповідальність.

## Форматування

- **Дужки Allman** — `{` на новому рядку.
- **`[SerializeField] private`** — для полів інспектора. Публічних полів для інспектора немає.
- **У ScriptableObject-конфігах**: `[field: SerializeField] public T Name { get; private set; }`.
- **Явні типи замість `var`** — `foreach (Flammable flammable in _flammables)`, а не `foreach (var flammable in ...)`.
- **Не більше одного порожнього рядка поспіль** — двох і більше порожніх рядків не ставимо.
- **Блоки `if` / `switch` / `for` / `foreach` / `while` відокремлюємо порожнім рядком** від сусіднього коду — візуально виділяємо структуру.
- **Перевірка на `false`**: `if (x == false)`, **а не** `if (!x)` — читається краще, знак оклику легко не помітити.
- **Між `case` у `switch` — порожній рядок** для читабельності.
- **Групуємо код порожніми рядками** між методами і логічними блоками — код не має перетворюватися на кашу з щільних рядків.
- Метод з одного виразу — expression-bodied (`=>`); якщо довгий, тіло переносимо на наступний рядок.

## Вміст

- **Жодних магічних чисел** — виносимо в іменовану `const` або поле, щоб було зрозуміло, за що відповідає значення. Допустимо `0`, якщо з контексту однозначно зрозуміло (наприклад, перевірка колекції на порожнечу).
- **Без обчислень у тексті, що виводиться** (`Debug.Log`, інтерполяція рядків) — у виводі очікуємо готовий результат, а не операції.
- **Прибираємо дублювання**: повторювані блоки коду → виносимо в метод.
- **Коментарі** — лише там, де незрозуміло «чому». Що робить код, має бути видно з назв.

## Unity

- `UnityEngine.Object` перевіряємо тільки через `== null` / `!= null`, не через `?.` і `??` (Unity перевизначає порівняння з null). `?.` — лише для звичайних C#-об'єктів (події, твіни).
- Підписка й відписка — завжди парами: `Awake`/`OnDestroy`, `Initialize`/`Dispose`.
- Без `FindObjectOfType`, синглтонів і статичного стану. `GetComponent` не викликаємо в `Update`.
- Ввід — лише через новий Input System (`UnityEngine.InputSystem`); старий `UnityEngine.Input` вимкнений у проєкті.

## Асинхронні методи

- **Тип повернення — `UniTask` / `UniTask<T>` / `UniTaskVoid`.** `Task` / `Task<T>` і корутини не використовуємо.
- **Суфікс `Async` у назві — обов'язковий** для будь-якого методу, що повертає `UniTask` / `UniTask<T>` / `UniTaskVoid`: `LoadSceneAsync`, `StartAsync`. Стосується і публічних, і приватних методів, і сигнатур в інтерфейсах.
- **`UniTaskVoid` — лише для fire-and-forget**, коли з контексту неможливо зробити `await` (наприклад, запуск із `Start()` MonoBehaviour-а). Назва — теж із суфіксом `Async`, виклик — з `.Forget()`.
- **`async void` — заборонено.** Єдиний допустимий виняток — обробник C#-події / UnityEvent, чия сигнатура жорстко вимагає `void`. Тоді тіло **обов'язково** в `try`/`catch`, інакше виняток зникне без сліду.
- **`CancellationToken` — останнім параметром**, назва — `cancellationToken`. Якщо в методу є необов'язкові параметри зі значеннями за замовчуванням — токен іде після них. Передавай токен в усі вкладені `*Async`-виклики всередині методу.
